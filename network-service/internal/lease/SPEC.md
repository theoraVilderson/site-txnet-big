# موتور مدیریت حجم چندپنلی — مشخصات پیاده‌سازی

> نسخهٔ نهایی الگوریتم «اجارهٔ حجم» بعد از رفع نقطه‌ضعف‌ها.
> هر ادعای عددی این سند از شبیه‌ساز همین مخزن آمده (`go run ./cmd/simreport`) و با `go test ./...` قابل تکرار است.

## ۰. خلاصه در یک صفحه

سه ایدهٔ اصلی عوض نشده، ولی هر سه سفت‌تر شده‌اند:

1. **دفتر کل مرکزی:** حجم واقعی کاربر فقط در دیتابیس ما نگه داشته می‌شود. پنل‌ها فقط شمارنده‌اند.
2. **اجارهٔ حجم:** به هر کانفیگ (رپلیکا) فقط یک «قسط» داده می‌شود. مجموع قسط‌ها به‌علاوهٔ ذخیرهٔ تأخیر پنل هیچ‌وقت از باقیماندهٔ کاربر بیشتر نمی‌شود.
3. **آشتی‌دهنده:** وضعیت مطلوب در صف ادغام‌شونده و اولویت‌دار نوشته می‌شود و پشت یک «دروازه» با نرخ تطبیقی به پنل می‌رسد.

چیزهایی که در این نسخه اضافه شد (همه با شبیه‌سازی پیدا و تأیید شده‌اند):

- **ساعت تیک پنل (TickClock):** پنل‌ها شمارنده را پله‌ای (هر J ثانیه) به‌روز می‌کنند. زمان واقعی هر داده را از روی تیک پنل حساب می‌کنیم و poll را درست بعد از تیک می‌زنیم. بدون این، خطای تخمین سرعت ±۱۰۰٪ بود.
- **کالیبراسیون خودکار تأخیر اعمال (Lag)** با نمونه‌های کامل و «سانسورشده».
- **ناوردای بدبینانه (LimitPeak):** بودجه فقط وقتی آزاد می‌شود که پنل کوچک شدن سقف را تأیید کرده باشد. در نتیجه در هیچ لحظه‌ای، حتی وسط نوشتن‌ها یا بعد از کرش، بیش‌تعهد رخ نمی‌دهد.
- **سه رژیم تصمیم:** عادی، پایانی (endgame) و بسته. قوانین باز و بسته شدن طوری تنظیم شده‌اند که قطع و وصل پشت‌سرهم (flap) و بن‌بست رخ ندهد.
- **حمل مانده/بدهی:** Quota و Used تجمعی‌اند. تمدید فقط `Quota += X` است، پس هر کسری یا اضافه‌ای خودکار به دورهٔ بعد منتقل می‌شود و در بلندمدت ضرر هیچ طرف صفر است.

نتیجهٔ ناوگان شبیه‌سازی‌شده (۶۰۰ کاربر، ۸ پنل، K=2، دو ساعت):

- p95 بیش‌مصرف: **+۰٫۳۷٪**
- میانه: **−۰٫۴۱٪**
- بدترین حالت: **+۲٫۹۵٪**
- قطعی کاذب (دستگاهی که حجم دارد ولی وصل نیست): **۰٫۰۰۷٪ زمان**
- ناوردا هیچ‌وقت نشکست.

## ۲. معماری و جریان داده

```
Next.js ──► Nest.js ──(outbox: create/renew/delete/move)──► Postgres ◄──┐
                                                                       │
                              ┌──────────────── Go engine ─────────────┤
                              │                                        │
   PanelWorker (هر پنل یکی)   │   Planner (هر حساب یک مالک)            │
   ┌──────────────────────┐   │   ┌───────────────────────────┐        │
   │ gate: AIMD+breaker   │   │   │ quota.Account.Plan()      │        │
   │ session single-flight│──►│──►│  (خالص، بدون I/O)          │──► SaveWants
   │ TickClock            │obs│   └───────────────────────────┘        │
   │ poll loop (heap/hint)│   │        │actions        │PollBy          │
   │ write loop ◄─ writeq │◄──┼────────┘               └──► hint ◄──────┘
   └──────────────────────┘
            │ HTTP (فقط اینجا)
            ▼
   Marzban / 3x-ui / Hiddify / MikroTik …
```

- Nest.js فقط **نیت** را ثبت می‌کند: خرید، تمدید، حذف، تغییر گروه. این کار با Outbox انجام می‌شود.
- Go تنها بخشی است که با پنل حرف می‌زند.
- مصرف نمایشی کاربر از `subscriptions.used_bytes` خوانده می‌شود، نه از پنل.
- ساب از کش ما سرو می‌شود (Redis یا CDN). کانفیگ‌ها موقع ساخت رپلیکا تولید و ذخیره می‌شوند.

## ۳. مدل داده

فایل کامل: `schema.sql`. مفاهیم:

| مفهوم | معنی |
|---|---|
| **Account** (subscription) | چیزی که کاربر خریده. `Quota` و `Used` تجمعی‌اند |
| **Replica** | یک شمارنده روی یک پنل برای یک حساب. در Marzban/Marzneshin/Hiddify یعنی کاربر روی آن پنل (همهٔ اینباندها یک شمارنده دارند). در 3x-ui/x-ui یعنی یک کلاینت روی یک اینباند |
| **Hold(r)** | `max(LimitPeak − Counter, 0)`: حداکثری که این رپلیکا بدون اینکه ما ببینیم می‌تواند مصرف کند |
| **LimitPeak** | بیشینهٔ سقف دیده‌شده و همهٔ سقف‌های درخواستیِ تأییدنشده (بدبینانه) |
| **Lag(panel)** | تأخیر بین رد شدن از سقف و قطع واقعی توسط پنل. خودکالیبره |
| **TickClock(panel)** | فاز تیک به‌روزرسانی شمارنده‌های پنل |

ناوردای ایمنی (اصلی که هیچ‌وقت نباید بشکند):

```
Used + Σ Hold(r) + Σ rate(r)·Lag(r)  ≤  Quota
```

تست `TestPlanNeverOvercommits` این ناوردا را روی ۲۰٬۰۰۰ حالت تصادفی بررسی می‌کند. شاخص `inv max` در شبیه‌ساز هم آن را پایش می‌کند.

## ۴. چرخهٔ هر poll (کد: `engine/engine.go`)

```
pollOnce(panel):
  snap ← gate.Do( adapter.Snapshot )          // یک درخواست برای کل پنل
  if خطا: panel.Healthy=false; همهٔ حساب‌های این پنل را re-plan کن; retry 15s; return
  panel.Clock.Observe(prevPoll, now, هر شمارنده‌ای عوض شد؟, کلاینت فعالی بود؟)
  برای هر رپلیکای این پنل:
      res ← account.Observe(r, snap[key])      // Delta، ری‌ست، نرخ، کالیبراسیون Lag، تأیید نوشتن
  Store.SaveObservations(فقط ردیف‌های تغییرکرده، CAS، یک تراکنش)
  برای هر حساب لمس‌شده: plan(account)

plan(account):
  res ← account.Plan(now, params)             // §۶
  Store.SaveWants(res.Actions)
  actions → writeq پنل مربوط (ادغام بر اساس replica، اولویت)
  PollBy → hint(panel) → AlignPoll → جلو کشیدن nextPoll

writeLoop(panel):
  ops ← queue.Pop (تا MaxBatch)؛ gate.Do( adapter.Apply )
  موفق ⇒ account.ConfirmWrite + plan(account)   // کوچک شدنِ تأییدشده ممکن است اجازهٔ بزرگ شدن بدهد
  ناموفق ⇒ دوباره در صف
```

## ۵. تخمین سرعت و ساعت تیک (`quota/rate.go`، `quota/tick.go`)

**مشکل.** 3x-ui و Marzban شمارنده‌ها را با یک job دوره‌ای (حدود ۱۰ ثانیه) به‌روز می‌کنند. عددی که در لحظهٔ t می‌خوانیم مصرفِ «تا آخرین تیک» است. اگر فاصلهٔ دو poll را مخرج بگیریم، یک poll پنج‌ثانیه‌ای ممکن است یک پلهٔ کامل ده‌ثانیه‌ای را ببیند (تخمین ۲ برابر) یا اصلاً چیزی نبیند (بیکار کاذب).

**TickClock.** همهٔ کلاینت‌های یک پنل با یک تیک به‌روز می‌شوند. هر poll یک مشاهده است:
- «در بازهٔ (prev, now] تیکی بود»، اگر هر شمارنده‌ای عوض شده باشد.
- «تیکی نبود»، اگر هیچ شمارنده‌ای عوض نشده ولی کلاینت فعال وجود داشته.

فاز J به ۳۲ بخش تقسیم می‌شود و یک bitmask از فازهای ممکن نگه داشته می‌شود. هر مشاهده این مجموعه را کوچک‌تر می‌کند. اگر مشاهده‌ها تناقض داشته باشند (مثلاً پنل ری‌استارت شده)، یادگیری از نو شروع می‌شود. با چند poll فاز با دقت J/32 پیدا می‌شود. سپس:
- `Effective(t)` = زمان آخرین تیک قبل از t. این زمانِ واقعی داده است.
- `AlignPoll(want)` = poll درست یک ثانیه بعد از تیک. poll بین دو تیک هیچ اطلاعات تازه‌ای ندارد.
- ⚠️ وقتی pollها دقیقاً هم‌تراز با تیک‌اند، دیگر مشاهدهٔ مفیدی تولید نمی‌کنند. زمان‌بند باید حدود هر ۵ دقیقه یک poll اضافه در وسط تیک (J/2) بزند تا اگر فاز جابه‌جا شد، فهمیده شود.

**قواعد Rate:**

1. نمونه فقط وقتی گرفته می‌شود که شمارنده عوض شده باشد. پنجره = `max(فاصلهٔ تیک‌ها, J)`.
2. اگر دو تیک هیچ تغییری نبود، آن رپلیکا بیکار است و Fast=0 فوراً. Slow به‌آرامی کم می‌شود.
3. وقتی رپلیکا قطع (blocked) بوده، نمونهٔ کم نادیده گرفته می‌شود. صفر در آن حالت یعنی «قطع است»، نه «بیکار است».
4. نمونهٔ اول بعد از بیداری = `d / max(فاصلهٔ همین poll, J)`: مصرف بعد از poll قبلی شروع شده، پس نه کل مدت بیکاری در مخرج است و نه فقط `J`. دو نمونه در حالت warm-up با سرعت اوج حساب.

- **Fast:** بالا رفتن فوری، پایین آمدن با EWMA ۳۰ ثانیه. برای ذخیرهٔ تأخیر، تقسیم پایانی و فوریت poll استفاده می‌شود.
- **Slow:** EWMA ده دقیقه. `Demand = max(Fast, Slow)` برای تعیین اندازهٔ قسط.

## ۶. تابع Plan (`quota/planner.go`)

### ۶-۱. ورودی‌های مشتق

```
برای هر رپلیکا:
  vNow = Fast,  vDem = max(Fast,Slow)   (در warm-up هر دو ≥ PeakReplica)
  hold = Hold(r)
  active = vNow > IdleRate
  blocked = !Exists || !EnabledSeen || Counter ≥ LimitSeen
  lagRes += vNow·Lag           (rate = vDem برای پنل ناسالم یا حالت واکنشی، که به آن PollInterval اضافه می‌شود)
remaining = Quota − Used
avail     = remaining − lagRes
frozen    = Σ hold روی پنل‌های ناسالم
availW    = avail − frozen                      // چیزی که واقعاً قابل تقسیم است
free      = avail − Σ hold                      // بودجه‌ای که همین الان آزاد است
tEnd      = avail / Σ vNow                      // چند ثانیه تا اتمام
```

### ۶-۲. باز و بسته شدن

```
بسته شود اگر: منقضی شده
           یا remaining ≤ 0
           یا (همهٔ رپلیکاهای فعال blocked هستند و avail < max(FinishMin, ΣvNow·FinishTime))
باز شود فقط اگر: Quota یا ExpiresAt عوض شده (تمدید) و avail ≥ ReopenMin
بستن = نوشتن enable=false (نه فقط limit=counter) ⇒ کاربر فوراً از Xray حذف می‌شود و منتظر job پنل نمی‌ماند
```

**چرا `avail ≤ 0` دلیل بستن نیست:** این شرط فقط یعنی «باقیمانده در مدت تأخیر پنل مصرف می‌شود»، و قسط‌ها قبلاً همین را حساب کرده‌اند. بستن در این لحظه به اندازهٔ `rate×Lag` کم‌تحویل می‌دهد. در شبیه‌سازی این اشتباه ۱۴٪ کم‌تحویل تولید کرد.

### ۶-۳. رژیم عادی (`tEnd ≥ Horizon`)

```
pool = availW·(1−ReserveFrac)                        // ۱۵٪ ذخیره برای شارژ فوری بدون نیاز به کوچک کردن دیگران
need_r = vDem·H(panel)   (فقط برای رپلیکای فعال)
H(panel) = max(Horizon, LowWater + 2·ActiveReplicas/WriteRate)   // پنل کُند ⇒ قسط بلندتر ⇒ نوشتن کمتر
surplus = pool − Σneed
  ۷۰٪ مازاد به رپلیکاهای فعال به نسبت need
  ۳۰٪ مازاد بین رپلیکاهای بیکار تقسیم مساوی   (IdleSurplusFrac)
target = clamp(need·scale + سهم مازاد,  floor,  MaxLease·Reliability)
floor  = max(MinLease, PeakRate·SwitchCover)

تصمیم (تنبل؛ فقط وقتی لازم است):
  blocked                               → regrant تا target            (فوری)
  effHold < low/2                       → regrant تا target            (فوری)
  effHold < low و target ≥ hold+MinStep → topup تا target
  effHold = hold − vNow·(now − زمان تیک داده)    ,   low = max(vDem·LowWater, MinLease/2)
```

در پلن‌های بزرگ، قسط هر رپلیکا چند گیگابایت است و تقریباً هیچ نوشتنی لازم نمی‌شود. شبیه‌ساز: پلن ۵۰ گیگ، دو ساعت، **۲ نوشتن** (همان دو ساخت اولیه).

### ۶-۴. رژیم پایانی (`tEnd < Horizon`)

```
tail = min(IdleTail, avail·10%/nIdle)            // رپلیکای بیکار هرگز صفر نمی‌شود (رپلیکای قطع نمی‌تواند تقاضایش را نشان دهد)
act  = availW − tail·nIdle
alloc_r = act · vNow_r / ΣvNow                   // همه با هم تمام می‌شوند
τ* = act / ΣvNow ,  τ_r = hold_r / vNow_r
  فعال و blocked و alloc ≥ FinishMin         → regrant alloc
  |τ_r − τ*| > max(EndgameTol, 20%·τ*)       → بازنویسی به alloc  (فقط اگر τ* > 2·(MinPoll+WriteLatency))
  بیکار و hold > tail+MinStep                → reclaim تا tail
```

شرط آخر مهم است: اگر زمان باقیمانده از زمانی که طول می‌کشد نوشتن برسد کمتر باشد، بازنویسی فقط باعث قطع و وصل پشت‌سرهم می‌شود. پس آن را بی‌خیال می‌شویم.

### ۶-۵. تسویه (settle): ایمنی دوفازی

```
۱. درخواست‌هایی که نوشتنشان در راه است یا فاصلهٔ حداقل (MinWriteGap/EndgameGap) را رعایت نمی‌کنند حذف می‌شوند. regrant استثناست.
۲. کوچک شدن‌ها فوراً نوشته می‌شوند، ولی LimitPeak تا تأیید پنل بالا می‌ماند.
۳. deficit = Σ(رشد لازم) − free   (یا −free اگر ناوردا از قبل شکسته باشد، مثلاً Lag بالا رفته)
   اهداکننده‌ها: رپلیکاهای بی‌اقدام با اضافه = hold − max(target, floor)؛ اول بیکارها، بعد بزرگ‌ترین اضافه
   حداقل اهدا = min(MinStep, deficit)    ← رفع بن‌بست پایانی
۴. رشد فقط از free فعلی، و اگر کم باشد به نسبت تقسیم می‌شود. بقیهٔ رشد در دور بعد، بعد از تأیید کوچک شدن‌ها، انجام می‌شود.
```

### ۶-۶. زمان‌بندی poll (خروجی PollBy)

```
فعال:    τ = hold/vNow − سن داده ;       poll تا τ/3      در بازهٔ [MinPoll, MaxPoll]
بیکار:   τ = hold/max(PeakReplica, BurstRate) ; poll تا τ/2   در بازهٔ [IdleMinPoll, MaxPoll]
نوشتن معوق: WriteLatency + 1s ,   نمونهٔ کالیبراسیون معوق: J + 1s
رژیم پایانی: حداکثر tEnd/3
nextPoll(panel) = min(همهٔ hintها) → AlignPoll → حداقل MinPoll بعد از poll قبلی
```

هزینهٔ poll به تعداد پنل‌ها بستگی دارد، نه تعداد کاربرها: یک درخواست همهٔ کلاینت‌های پنل را برمی‌گرداند. در ناوگان شبیه‌سازی‌شده، هر پنل حدوداً هر ۱۳ ثانیه یک poll داشت. برای پنل‌های خیلی بزرگ (پاسخ چندمگابایتی) یک `MinPoll` اختصاصی بگذار.

## ۷. کالیبراسیون Lag (`quota/lag.go`، `quota/ledger.go`)

- **نمونهٔ کامل:** پنل خودش کلاینت را قطع کرد (enabled از true به false، با شمارنده ≥ سقف). بعد از یک تیک کامل بدون تغییر، `lag = (counter − limit) / rate` ثبت می‌شود. شرط اعتبار: سرعت با حداقل ۲ نمونه اندازه‌گیری شده و در حال warm-up نیست. بدون این شرط، سرعتِ کم‌تخمین‌زده lag را ۷۸ ثانیه نشان می‌داد در حالی که واقعی ۲۵ ثانیه بود.
- **نمونهٔ سانسورشده:** شمارنده از سقف رد شده ولی پنل هنوز قطع نکرده. پس lag دست‌کم `(counter−limit)/rate` است. اگر این مقدار از تخمین فعلی بیشتر باشد، ثبت می‌شود. بدون آن، پنلی که کُندتر از تخمین ماست هیچ‌وقت کالیبره نمی‌شود، چون ما زودتر می‌بندیم.
- EWMA میانگین و واریانس با α=0.2. ذخیره = `mean + LagZ·σ`.
  - `LagZ=0`: بی‌طرف، یعنی بیش و کم به یک اندازه محتمل‌اند. با حمل مانده، ضرر بلندمدت صفر است.
  - `LagZ=1`: به‌ندرت بیش‌تحویل، به قیمت کمی کم‌تحویل.
- مقدار اولیه `0.75·J` است. Lag را در جدول `panels` ذخیره کن تا بعد از ری‌استارت از نو یاد نگیرد.
- **سقف دقت:** تیک پنل در هر لحظه‌ای بین ۰ و J ممکن است بیفتد. پس حتی با Lag کاملاً کالیبره، خطای هر قطع به‌طور ذاتی حدود `v·J/√12` است: در ۸ MB/s و J=۳۰ ثانیه حدود ±۷۰ مگ. این خطا با حمل مانده صفر می‌شود (ستون دوره‌ها در گزارش شبیه‌ساز).

## ۸. مقیاس‌پذیری

| مؤلفه | هزینه |
|---|---|
| `Plan()` | **۰٫۷ میکروثانیه** برای حساب ۳ رپلیکایی (benchmark)، یعنی بیش از ۱ میلیون plan در ثانیه روی یک هسته |
| poll | یک درخواست برای هر پنل در هر ۱۰ تا ۳۰۰ ثانیه. مستقل از تعداد کاربر |
| ذخیره | یک UPDATE دسته‌ای (`unnest`) برای هر poll، فقط ردیف‌های تغییرکرده |
| حافظه | حدود ۴۰۰ بایت برای هر رپلیکا. ۵ میلیون رپلیکا حدود ۲ گیگابایت، قابل شارد |
| نوشتن | در عمر هر حساب ۱۰ تا ۲۰ نوشتن (ساخت، چند شارژ، تقسیم پایانی، بستن). برای پلن ۳۰ روزه و ۵۰۰۰ کاربر روی یک پنل، حدود ۰٫۰۳ نوشتن در ثانیه |

**شاردینگ** وقتی لازم است که پنل‌ها از چند هزار بیشتر شوند:

- **پنل ⟵ نود:** با rendezvous hashing روی نودهای زنده و lease در `panels.owner_node`. هر پنل دقیقاً یک poller و یک gate دارد، پس rate limit دقیق است.
- **حساب ⟵ نود:** بر اساس `hash(sub_id)`. رپلیکاهای یک حساب روی پنل‌های نودهای مختلف‌اند، پس poller مشاهده‌ها را به planner صاحب حساب می‌فرستد (NATS JetStream یا Redis Streams، پارتیشن با sub_id). planner اکشن‌ها را به صاحب پنل برمی‌گرداند (پارتیشن با panel_id).
- **نسخهٔ ساده‌تر برای شروع:** هر حساب فقط در گروه‌هایی که همهٔ پنل‌هایشان مال یک نماینده‌اند. پس شارد با `tenant_id` هر دو محور را هم‌زمان پوشش می‌دهد و تا ده‌ها هزار پنل پیام‌رسانی بین نودی لازم نیست.

| **Marzneshin** | مشابه، ولی با مفهوم «service» به جای inbound | — | یک رپلیکا برای هر کاربر |
| **Hiddify** | API v2 ادمین | — | حجم GB اعشاری است و به بایت تبدیل می‌شود. به‌روزرسانی مصرف کُندتر است، پس J بزرگ‌تر بگذار؛ کالیبراسیون بقیه را درست می‌کند |

**قواعد مشترک:**

- کلید کلاینت قطعی باشد (مثلاً `u{sub}_r{replica}`) و UUID با `UUIDv5(sub, replica)` ساخته شود. retry هیچ‌وقت کلاینت تکراری نمی‌سازد.
- هیچ کلاینتی بدون سقف نماند. `0` در این پنل‌ها یعنی «نامحدود».
- expiry پنل را هم به‌عنوان پشتیبان تنظیم کن، ولی منبع حقیقت انقضا موتور ماست.
- آداپتر «احمق» بماند: بدون retry، بدون rate limit، بدون منطق. این‌ها کار gate و planner است.

**امنیت (پنل‌ها را نماینده‌ها اضافه می‌کنند):**

- URL پنل: resolve کن و IPهای خصوصی، loopback، link-local و `169.254.169.254` را رد کن. redirect به این‌ها ممنوع. dial را به IP تأییدشده pin کن (در برابر DNS rebinding).
- پاسخ‌ها را با `io.LimitReader` (مثلاً ۵۰ مگابایت) و timeout محدود کن.
- اعتبارنامه‌ها رمزنگاری‌شده ذخیره شوند.
- هر نماینده فقط پنل‌های خودش را در گروه‌هایش می‌بیند.

## ۱۲. ترتیب پیاده‌سازی

1. `quota` و `sim` همین مخزن را بدون تغییر بیاور. هر تغییری بده، `go test ./...` باید سبز بماند.
2. آداپتر 3x-ui v2 و Marzban. تست قراردادی روی پنل واقعی: Snapshot، ساخت، سقف، enable/disable، ری‌ست.
3. `engine` + Store روی Postgres (`schema.sql`): SaveObservations با CAS، SaveWants، بارگذاری در استارت. Lag و TickClock هم ذخیره شوند.
4. سرویس ساب از کش + تولید کانفیگ هنگام ساخت رپلیکا.
5. Outbox بین Nest و Go (خرید، تمدید، حذف، تغییر گروه با HRW از پکیج `hrw`).
6. متریک‌ها و داشبورد (§۱۰)، و بعد تنظیم پارامترها با دادهٔ واقعی.
7. بقیهٔ آداپترها (Marzneshin، 3x-ui v3، alireza0، Hiddify، MikroTik).
8. شاردینگ (§۸)، فقط وقتی یک نود کم آمد.

**نقشهٔ فایل‌ها:**

| فایل | محتوا |
|---|---|
| `quota/types.go` | Account، Replica، PanelState، Hold |
| `quota/ledger.go` | Observe، Delta، کالیبراسیون، ConfirmWrite |
| `quota/planner.go` | Plan و همهٔ رژیم‌ها |
| `quota/rate.go` | تخمین سرعت |
| `quota/tick.go` | TickClock |
| `quota/lag.go` | Lag |
| `quota/params.go` | پارامترها |
| `writeq/` | صف ادغامی اولویت‌دار |
| `gate/` | AIMD، breaker، Retry-After، single-flight login |
| `hrw/` | انتخاب K از N |
| `engine/` | پیاده‌سازی مرجع poll/write/plan + رابط Adapter و Store |
| `sim/` | شبیه‌ساز + سناریوهای رگرسیون |
| `cmd/simreport` | گزارش |
| `cmd/simtrace` | ردگیری قدم‌به‌قدم یک سناریو، برای دیباگ هر تغییر |
